# Gurach — план автоподбора метаданных при загрузке трека

**Статус:** план для реализации. В этом документе нет выполненных этапов. Основной выпуск охватывает запись, релиз, альбом, жанры и обложку. Второй выпуск добавляет текст из внешнего источника. Ручной ввод текста входит в оба выпуска.

## Пользовательский сценарий и граница подтверждения

Пользователь выбирает аудио, вводит название и исполнителя. Галочка «Подобрать метаданные» включена по умолчанию. Через 700 мс после паузы в наборе форма показывает подходящий релиз с обложкой и жанрами или список до пяти вариантов. По одному названию поиск запускается кнопкой «Найти по названию». Внешним сервисам передаются поисковые поля. Аудиофайл остаётся в браузере до отправки формы.

Карточка предложения показывает название, исполнителя, версию, альбом, год и длительность, если они известны. Пользователь выбирает поля и нажимает «Применить». Это меняет только черновик. Запись в библиотеке появляется после «Загрузить» и успешной публикации. Найденное значение можно исправить или удалить. При выключении галочки применённые значения остаются в черновике, новые обращения прекращаются. Если обложка отсутствует, форма предлагает выбрать локальную картинку — для публикации Gurach уже требует файл обложки. Если отсутствуют жанры, альбом или текст, их можно оставить пустыми.

## Этап 1. Зафиксировать контракт и провести ручные поля через публикацию

Этот этап даёт проверяемый результат до подключения каталогов. Вручную заданные альбом и жанры должны переживать загрузку, фоновую обработку и последующее редактирование.

1. Добавить в Track необязательные album, genres, externalIds и сведения о происхождении полей. Предлагаемые пределы для первой версии — 200 символов для альбома, до 16 жанров по 80 символов. Для externalIds определить recordingMbid и releaseMbid формата UUID. Старые треки при чтении дают album: null и genres: []. Историческим записям не приписывать происхождение задним числом.
2. Для multipart добавить **одно** необязательное текстовое поле catalogMetadata с ограниченным JSON (предлагаемый предел 16 КиБ UTF-8). Пример для ручного ввода приведён ниже. Поля name, artist, text, duration и файлы picture, audio продолжают передаваться прежним способом. В file-policy.ts увеличить maxBodyFields с 4 до 5, разрешить имя и предел размера. В DTO один раз разобрать и валидировать объект, включая вложенные типы, допустимые ключи, длины, перечисления, UUID и уникальность жанров. Некорректная структура даёт 400. Обе multipart-схемы в track.controller.ts должны документировать сериализованную строку.
3. Для предложения сохранять происхождение применённых полей отдельно, например albumSource, pictureSource и список genreEvidence с полями genre, rawTag, source, scope, confidence. confidence — оценка Gurach в диапазоне 0–1. Хранить доказательства только для оставшихся жанров. Ручной ввод допускает жанр вне словаря. Для исправленных полей указывать ручное происхождение. Переданные клиентом источники означают выбор пользователя, а не независимую проверку каталогом. Старым клиентам сведения о происхождении передавать не требуется.
4. Добавить тип подтверждённых значений в MediaOperation.upload. Сохранить их в enqueue, восстановить в processUpload и явно передать разрешённые поля в транзакцию create. Проверить также прямой POST /tracks. Воркер использует сохранённый снимок и локальные файлы, в том числе при повторной попытке. Ключи уникальности и фактическую длительность аудио по-прежнему определяет сервер.
5. Обновить TrackDetail, toTrackDetail и проекции getOne/update. В редакторе и на странице трека вывести альбом и жанры. Для PATCH /tracks/:id использовать обычные JSON-поля album и genres. Пропуск поля сохраняет прежнее значение, пустая строка и пустой массив очищают соответствующие поля. Расширить UpdateTrackDto, проверку непустого PATCH в сервисе и список ключей в client/app/api/tracks/[id]/route.ts. Редактор сегодня отправляет все поля. Передавать изменения или сравнивать значения на сервере, чтобы обычное сохранение не сбрасывало происхождение. При смене идентичности записи убрать устаревшие внешние привязки, при ручной смене релиза отвязать releaseMbid. Сохранить существующие проверки владельца, ответ 409 для дубликата и событие track.updated.

Пример значения catalogMetadata для загрузки без обращения к каталогам:

```json
{"album":"Example EP","genres":["Ambient","Dub techno"]}
```

**Готово, когда** прямой запрос возвращает 201 с новыми полями, фоновый — 202, а после published запрос детального трека возвращает те же значения. Ручной PATCH одного поля сохраняет остальные. Старый multipart и ранее созданная операция без catalogMetadata продолжают обрабатываться.

## Этап 2. Поиск записи и выбор издания

Добавить серверный модуль server/src/metadata, подключить в app.module.ts. Вынести вызовы внешних сервисов в провайдеры, оценку совпадений — в тестируемую функцию. Браузер обращается только к одноимённым маршрутам Gurach. Контракты ниже — новые маршруты, предлагаемые к реализации.

| Браузер → NestJS | Вход | Успешный результат |
|---|---|---|
| POST /api/metadata/search → /metadata/search | name, необязательные artist, durationMs | 200 с candidates и recommendedIndex либо null. Каждый вариант содержит name, artist, version, durationMs, recordingMbid, выбранный releaseMbid, album, year, confidence и sources. Отсутствующие значения явно обозначать null. |
| POST /api/metadata/details → /metadata/details | recordingMbid и необязательный releaseMbid | 200 с подтверждённой парой запись/релиз, доступными полями, genreEvidence, ссылкой на внутренний маршрут обложки и статусами источников. Принадлежность релиза записи проверять до объединения полей. |
| GET /api/metadata/artwork/:releaseMbid → /metadata/artwork/:releaseMbid | UUID из выбранного издания | Файл миниатюры с корректным Content-Type, 404 при отсутствии. Подробнее в этапе 4. |

* На BFF использовать действующую сессию, checkBrowserMutation для POST, readBoundedJson, передачу request.signal и x-request-id. NestJS требует того же авторизованного пользователя, что и загрузка. Лимитировать входящие запросы. Не резервировать квоту загрузки для поискового запроса.
* Проверять длину name и artist по правилам загрузки. На поиске durationMs — конечное целое от 0 до 3 600 000. Текущий upload.duration измеряется в секундах. Подсказку длительности брать из metadata выбранного браузером аудиофайла, когда формат это позволяет. Ошибка чтения оставляет поиск доступным.
* В MusicBrainz искать recording по названию и исполнителю с экранированием специальных символов поискового синтаксиса. Для сравнения нормализовать Unicode, регистр и пробелы. Сохранять исходное написание для показа. Отделять пометки Live, Remix, Radio Edit, Extended от базового названия для отдельного сравнения. Один recording может иметь несколько релизов. Свести дубли одного издания, сохранить различимые варианты альбома. При нескольких изданиях предложить выбор перед подстановкой обложки.
* Начальная эвристика для записи: 0,40 × сходство названия + 0,35 × сходство исполнителя + 0,15 × близость длительности + 0,10 × совпадение версии. Определить сходство, например через нормированное редакционное расстояние строк, близость длительности — линейно от 1 при разнице до 2 с до 0 при разнице 20 с. Делить сумму на вес доступных признаков. Явный конфликт версий исключает автоматическую рекомендацию. Начальные условия рекомендации — указан исполнитель, оценка ≥ 0,90, отрыв от второго варианта ≥ 0,08 и однозначный релиз. Начиная с 0,70 показывать варианты. При более слабом результате предложить уточнить запрос. Пороги покрыть примерами и корректировать по результатам проверки. Это оценка ранжирования, не вероятность.
* Настроить осмысленный User-Agent Gurach с версией и контактом. Ограничить **все** обращения к MusicBrainz, включая details и повторы, одним стартом запроса в секунду на общий исходящий IP. Для нескольких реплик использовать общий ограничитель, например атомарное занятие временного слота в Mongo по часам БД непосредственно перед вызовом. Ожидание ограничить общим дедлайном запроса. Проверить двумя экземплярами сервиса с одним хранилищем. При 429/503 учитывать Retry-After, отбрасывать отменённые ожидания.
* Предлагаемые исходные значения — тайм-аут провайдера 4 с, ограниченный кэш в памяти до 500 записей на экземпляр, успешный результат 15 минут, пустой 1 минуту. Ошибку связи отличать от пустой выдачи. Ключ поиска включает нормализованные название с версией, исполнителя и длительность. Ключ подробностей включает оба MBID. Объединять одинаковые параллельные запросы, снимая работу из очереди, когда последний ожидающий клиент отменил запрос. Для настроек и серверных ключей сверить .env.example, конфигурацию контейнеров и server/src/common/env-validation.ts.

Документация источника — [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API), [поиск записей](https://musicbrainz.org/doc/MusicBrainz_API/Search), [лимиты](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting).

**Готово, когда** тесты с фиксированными ответами различают одноимённые записи, studio/live, близкие оценки и два издания одной записи. Запрос по одному названию никогда не выбирает вариант автоматически.

## Этап 3. Дополнить выбранный релиз жанрами

1. Сначала запросить жанры записи MusicBrainz. При наличии серверного LASTFM_API_KEY вызвать track.getInfo для выбранной записи, предпочесть MBID, иначе использовать пару исполнитель/название и проверить совпадение версии. Не привязывать найденный Last.fm альбом к другому выбранному релизу.
2. Если принятых жанров трека нет, попробовать уровень релиза через MusicBrainz или album.getInfo для совпавшего альбома. Жанры исполнителя, если включены как резерв, выдавать отдельными неподтверждёнными предложениями с подписью «жанр исполнителя».
3. Предусмотреть небольшой проверяемый словарь жанров и явных псевдонимов для тегов Last.fm. Сравнивать регистр и пробелы, объединять только утверждённые синонимы. Например, seen live исключать, а electronica и electronic music не объединять без правила. Для каждой рекомендации возвращать исходный тег, источник, уровень и оценку по документированной эвристике (например, стартовые 0,90 / 0,70 / 0,50 для записи / релиза / исполнителя при точном совпадении со словарём). Отсутствие ключа или отказ Last.fm означает частичный ответ.
4. Проверить условия использования подключаемых источников для режима работы Gurach, включая указание источника в интерфейсе. RYM подключать отдельным провайдером при наличии разрешённого программного доступа. Массовая загрузка, AcoustID и повторное использование метаданных библиотеки — отдельные улучшения после первого выпуска.

Документация — [Last.fm track.getInfo](https://www.last.fm/api/show/track.getInfo), [Last.fm album.getInfo](https://www.last.fm/api/show/album.getInfo), [условия Last.fm API](https://www.last.fm/api/tos).

**Готово, когда** с отключённым Last.fm доступен результат MusicBrainz, произвольный тег не становится жанром и в форме видно происхождение каждого предложенного жанра.

## Этап 4. Передать обложку через существующую загрузку

1. Сервер строит запрос к Cover Art Archive по проверенному releaseMbid, вариант front-500. Входной параметр — UUID. Разрешать HTTPS и проверенные адреса CDN архива на каждом редиректе, ограничить число переходов, время и объём чтения даже без Content-Length. При 404 показывать «У этого издания нет обложки», при временной ошибке — возможность повторить. Перед публикацией сверить применимые условия использования изображений.
2. Добавить или переиспользовать авторизованный **бинарный** BFF-маршрут. Успешный ответ передавать байтами с проверенным типом изображения, ограничить размер действующим maxCoverBytes (10 МиБ). Текстовый proxyBackend для байтов не подходит. Не передавать внешнему сервису сессию Gurach. Проверить маршрут бинарным файлом со сравнением исходных и полученных байтов.
3. В форме получить изображение один раз для выбранного релиза, сохранить Blob/File, показать через object URL. Создавать имя файла по проверенному формату. Освобождать URL при смене и размонтировании. Применённый файл держать до завершения или смены обложки. Переключение предложения не удаляет применённый файл из черновика.
4. У UploadFileField ввести параметр required с прежним значением по умолчанию. Для picture снять обязательность нативного input при наличии принятого файла. На submit подставить его через FormData.set('picture', file, filename). Выбранная вручную обложка имеет приоритет. При её удалении явно показать, какой файл теперь будет отправлен. Проверка типа, размера, декодирования и обработка дубликатов при публикации идут по обычному пути.

Документация — [Cover Art Archive API](https://musicbrainz.org/doc/Cover_Art_Archive/API).

**Готово, когда** пользователь загружает трек без открытия локального выбора картинки, видит ту же обложку после публикации, а подмена собственной картинкой и сценарий 404 работают.

## Этап 5. Собрать форму и обработать смену состояния

* В client/features/tracks/hooks добавить useMetadataLookup. Разделить состояние поиска, карточку предложения и значения формы. Держать собственный AbortController поиска отдельно от существующего контроллера загрузки. Искать только при активной сессии и редактируемом черновике. При возобновлённом опросе operationId поиск не запускается.
* Обновление названия, исполнителя или файла инвалидирует старую выдачу. Сверять номер актуального запроса после каждого await, включая подробности и загрузку обложки. Смена кандидата сбрасывает неприменённые предложения предыдущего. При смене идентичности трека очищать ранее автоматически заполненные зависимые значения и привязки, сохраняя ручные правки. При отключении автопоиска сохранить применённый черновик целиком. При закрытии формы и перед submit отменять таймер и текущий поиск. Запрос, уже полученный внешним сервисом, отменить задним числом невозможно.
* Хранить признак ручного изменения каждого поля, включая намеренно пустое значение. По умолчанию «Применить» выбирает доступные поля, которые пользователь ещё не менял. Для замены своей обложки или своего альбома нужно явно отметить соответствующее поле. Удалённый пользователем жанр не должен возвращаться с запоздалым ответом. Для введённых пользователем названия и исполнителя оставить возможность явной коррекции по каталогу.
* Ввести редактируемые album и genres даже при отключённом поиске. Статусы «Ищем», «Выберите версию», «Совпадений нет», «Источник временно недоступен» и «Применено» локализовать в client/messages/ru.json и en.json. Сделать список доступным с клавиатуры и озвучивать смену статуса. Публикация вручную доступна, пока внешний поиск ожидает ответа.
* Зарегистрировать MetadataController в server/src/contracts/api-controller.registry.ts и зависимости для офлайн-генерации в document.module.ts. Обновить server/openapi.json и client/lib/api/schema.d.ts командами генерации. Сверить клиентские типы TrackDetail и типы запросов с полученной схемой.

**Готово, когда** сценарий от выбора файла до карточки трека проходит через штатную форму, включая ручную правку после «Применить», отмену старого запроса и возобновление фоновой загрузки.

## Этап 6. Автоматический текст песни — второй выпуск

* Условие старта внешней интеграции — у Gurach есть доступ к провайдеру и условия для нужных действий: получение полного текста, редактирование, хранение и показ на странице. Кандидат — [официальный API Musixmatch](https://github.com/musixmatch/musixmatch-sdk). Зафиксировать допустимые операции, атрибуцию и ограничения конкретного доступа до выбора схемы хранения. Сам факт выдачи API-ключа не подтверждает эти возможности.
* Добавить опциональный серверный провайдер в details. По возможности использовать ISRC выбранной записи, иначе сверять название, исполнителя и версию. Возвращать отдельные состояния «доступен», «инструментал», «не найден», «источник недоступен» и «показ ограничен». Не подставлять биографию, аннотацию или фрагмент как полный текст.
* При доступе для полного сценария добавить предлагаемый текст и источник в карточку, свести подтверждение к действующему полю text, применять лимит 100 000 символов. Если договор допускает только показ, реализовать допускаемый способ показа отдельно и оставить поле ввода для собственного текста пользователя. В отчёте явно указать, доступен ли именно сценарий сохранения полного текста.
* Проверить инструментал, отличающуюся версию, пустой ответ и собственный текст пользователя. Без доступа к провайдеру сдать первый выпуск отдельно, записать конкретную зависимость второго в отчёт. Приёмка автотекста требует работающего разрешённого источника.

## Проверки и передача результата

| Уровень | Что обязательно воспроизвести |
|---|---|
| Unit, сервер | Нормализация кириллицы и латиницы, экранирование спецсимволов, отсутствующая длительность, конфликт версий, переиздания, fallback жанров, кэш и отмена ожидающей работы, тайм-аут, 429/503, отсутствие ключа. Успехи, пустые ответы и недоступность различимы. |
| Контракт и интеграция | Авторизация новых маршрутов, отклонение неизвестных/слишком длинных полей, старый multipart, новый multipart в режимах 201 и 202, чтение после публикации, восстановление старой и новой операции, 409 для дубликата, PATCH владельца и запрет для постороннего. Происхождение соответствует итоговым полям. |
| Обложки | Редирект архива, неверный тип, 404 и превышение 10 МиБ при потоковой передаче. В BFF проверить побайтовое совпадение, в интеграции — публикацию файла через обычный media validator. |
| Браузер | Расширить client/tests/e2e/api-fixture.mjs и upload.spec.ts. Проверить автообложку, близкие результаты, выбор конкретного релиза, ручную замену, пустые поля, быстрый ввод A → B с поздним ответом A, выключение во время поиска и 0 запросов при выключенной галочке, восстановление после 202, отображение сохранённых полей и PATCH из редактора. |

Запускать команды из корня. Для воспроизводимых проверок использовать версию Node из .node-version. Интеграционным тестам нужны Docker и медиазависимости проекта. В CI внешние ответы подменять фиксированными данными. Отдельно перед релизом выполнить пробу MusicBrainz → выбранный релиз → Cover Art Archive с сетевым доступом и настроенным User-Agent, затем проверить Last.fm, если подключён ключ. В отчёте различать успешную фикстуру и успешный живой запрос.

**Приёмка первого выпуска.** На форме выбрать аудио, ввести название и исполнителя, применить найденный релиз и загрузить без локальной обложки. После published и перезагрузки должны совпадать обложка, подтверждённые жанры и альбом с учётом ручных правок. Повторить загрузку другим файлом при отключённой галочке и проверить отсутствие обращений к каталогам. Выполнить проверки частичного ответа и неоднозначного совпадения. Зафиксировать реализованные этапы, команды и результаты, проверенные живые источники, необходимые переменные окружения и состояние интеграции текстов.
