# Взаимная дружба

## Область реализации

Авторизованные пользователи могут искать аккаунты по началу username, открывать
профиль, отправлять, отменять, принимать и отклонять заявки, удалять друзей и
независимо блокировать друг друга. Страницы: `/friends`, `/users/[username]`.
На странице `/account` показаны первые пять друзей в порядке списка
(сначала недавно добавленные), со ссылками на профили и кнопкой «Все друзья».
Статистика аккаунта включает общее число друзей из `/friends/summary`.
Список запрашивается через BFF с `count=5`, обновляется при возвращении фокуса
и сбрасывается при смене аккаунта; учёт прослушиваний не вызывает его перезагрузку.

Главная страница, плеер, очередь и музыкальные API не изменяются.

Nest использует существующие `SessionGuard` и `CurrentActor`. Браузер обращается
только к соответствующим маршрутам Next BFF; мутации проходят проверку CSRF,
параметров и ограниченного JSON. Ответы приватные и не кешируются.

## Хранение и конкуренция

`social_relations` содержит одну каноническую пару ObjectId, статус
`none | pending | accepted`, UUID активной заявки, независимые флаги блокировки,
монотонную ревизию и cooldown. Документы не удаляются после отмены, удаления
дружбы и блокировки. Разблокировка не восстанавливает дружбу.

Принятие, отмена и отклонение привязаны к UUID конкретной заявки.
Удаление друга, блокировка и разблокировка принимают обязательный query-параметр
`expectedRevision`. Значение `0` обозначает отсутствие документа, остальные
значения берутся из `relationship.revision`. Потеря гонки возвращает `409`.
Клиент перечитывает состояние после конфликта.

Новая заявка и квота согласуются MongoDB-транзакцией. Нужен replica set (как для
существующих операций с сессиями и прослушиваниями). В
`friend_request_counters` уникальный ключ `(userId, day)`:
UTC-дата учитывает дневную квоту, специальный день `*` сериализует admission
одного отправителя даже при переходе через полночь. Неуспешные и повторные
заявки не расходуют квоту. Новые зависимости не добавлены.

Лимиты: 30 новых заявок в сутки, 50 активных исходящих; cooldown после отмены —
5 минут, отклонения и удаления из друзей — 24 часа. Ответ `429` содержит
`Retry-After`; для заполненного списка исходящих это 60 секунд до повторной
проверки, освобождение места зависит от обработки заявок.

Курсоры содержат пару ключей сортировки и SHA-256 области (пользователь, вид
списка, поисковая строка). Списки упорядочены по времени и `_id`, блокировки —
по `_id`, поиск — по `username` и `_id`. Лимит страницы по умолчанию 20,
максимум 50. Профили списков разрешаются в MongoDB через `$lookup` до лимита;
поиск исключает заблокированные ID до лимита и пакетно читает отношения.
Отключённые аккаунты скрыты, но остаются в собственном списке блокировок для
возможности разблокировки. Приватные поля пользователей не сериализуются.
Блокировка другой стороной отображается как недоступная сущность (`404`).

Клиент отменяет устаревшие запросы, задерживает поиск на 300 мс, блокирует
повторное действие с тем же отношением и сбрасывает приватное состояние при
смене аккаунта. На странице друзей после успешного действия перечитываются
затронутый открытый список, результаты поиска и сводка; закрытые вкладки
загружаются при открытии. После конфликта актуальность всех вкладок сбрасывается.

## Установка индексов

Миграция `007-social-relations` зарегистрирована в общем runner. Создаёт:

- `relation_pair_unique`, `relation_request_unique` (partial unique).
- `relation_incoming`, `relation_outgoing`.
- `relation_friends_low`, `relation_friends_high`.
- `relation_blocks_low`, `relation_blocks_high`.
- `friend_request_counter_unique`.
- `user_username_page` на существующей коллекции `users`.

`verify()` миграции сверяет имена, ключи, unique, sparse,
partialFilterExpression, TTL и отсутствие неожиданной collation.
Миграция не содержит backfill и не изменяет пользовательские документы.
При запуске приложения социальные индексы автоматически не устанавливаются.
До эксплуатации необходимо отдельно согласовать и применить миграцию.
Ограничения существующего runner на целевую БД сохраняются: apply разрешён
только для `gurach_test_*`; процедура установки в рабочую БД требует отдельного
решения, без обхода защит runner.

План запроса поиска (`explain('executionStats')`) нужно исследовать на целевой
БД после установки индексов и до выпуска. Подключений к реальной БД для
реализации не выполнялось.

## Контракты и валидация

Метаданные контроллеров включены в offline OpenAPI-модуль.
Обновление контракта: `npm run openapi:generate --prefix server`, затем
`npm run api:generate --prefix client`. Клиентские типы берутся из
`client/lib/api/schema.d.ts`.

По последнему указанию пользователя новые тесты не создавались и проверки
(typecheck, lint, build, контрактные и интеграционные) не запускались.
Выполнена только генерация OpenAPI и TypeScript API-типов; штатная генерация
OpenAPI включает компиляцию tools. Конкурентные сценарии с исследованием
конечного состояния MongoDB и проверка UI/плеера не выполнялись.
